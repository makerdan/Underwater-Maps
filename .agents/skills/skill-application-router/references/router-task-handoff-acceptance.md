# Router primary-task handoff acceptance

These are required host acceptance cases for this handoff, not a claim that
task APIs or executable host tests are installed in this package. Structural
document/package checks cannot prove live task creation or dependency behavior.
Apply the mandatory [binding and recovery protocol](handoff-binding-and-recovery.md)
to every case. Symbolic inputs below are test scenarios, not real host records.

| Case | Required behavior and evidence |
|---|---|
| New primary | Confirmed committed success plus authoritative finalized plan readback permits creating the dependent verifier; a pending writer does not. Uncertain responses use authoritative recovery rather than blind retry. |
| Existing surfaced Install/Apply | A task surfaced by Replit Agent with a real ID, matching Project/target/scope, and authoritative finalized durable plan permits the same handoff without a create response or new write in this invocation. Reuse that primary, never create a duplicate to qualify. |
| Surfaced durable Draft/Plan | Draft/Plan status does not disqualify a finalized durable primary plan. Create only the pending dependent verifier; do not approve or activate either task. |
| Suggestion or uncommitted draft | A title/card, chat suggestion, guessed ID, or status with no verified durable finalized record cannot trigger successful handoff. Report what evidence is missing. |
| Wrong or ambiguous primary | Wrong Project, target skill, scope, plan/version/digest, dependency state, or ambiguous primary selection blocks linkage; another task's valid ID cannot be substituted. |
| Finalization and mutation | An already finalized existing record needs no artificial rewrite. An active writer uses bounded polling; timer-only, unchanged repeated reads, plan changes during the barrier, missing finalization evidence, and timeout remain blocked. |
| Failed/cancelled primary | Do not create an installation verifier depending on an undeliverable failed/cancelled primary; report remediation separately without reopening or duplicating it. |
| Completed surfaced primary | Use the delivered outcome only with real delivery evidence and the verified primary-record barrier; Ready/Done status alone cannot prove installation or implementation. |
| Repeated surfacing and duplicate race | The same normalized, persisted Project/target/primary namespace-ID/committed primary-plan digest/scope key returns the valid existing verifier rather than creating another. Check payload, lifecycle, and evidence too. Use atomic idempotency when available; otherwise report non-atomic risk and reconcile duplicates without silent deletion. |
| Source becomes available | Create a pending verifier while the planned canonical destination is absent, deliver installation, then resurface that same primary/plan/scope. Newly available source evidence does not change its key; the original verifier ID and actual dependency are reused. |
| Legacy key and drift | Search matching legacy source-or-plan keys before creating, validate their primary-plan/scope/dependency binding, and reuse valid records. Conflicting records report blocked. Changed primary-plan version/scope requires explicit renewed binding; changed source evidence is not silently accepted as a pass or used to produce a duplicate. |
| Dependency creation/readback | The new verifier has a real host dependency on the reused primary. Compare the complete persisted payload/coverage, report path, primary link, key, and lifecycle, with primary-version checks before/after attachment. Missing creator/dependency/readiness routes, guessed IDs, mismatched links, or truncated payloads report blocked, not successfully linked. |
| Companion confirmation | Preserve the target's required file-only confirmation workflow. Existing primaries do not get recreated to fake a same-call history; missing companion obligations use the permitted repair route or are reported blocked. Independent verification is not silently dropped. |
| No recursion or approval side effects | A surfaced verification task is not an Install/Apply primary. Creating a verifier does not trigger another, approve/activate tasks, mark checks passed, or control platform completion. |
| Direct verification-only request | Delivery of a requested evidence-linked plan requires no unrelated Install/Apply primary or automatic follow-up; requested but unavailable host task creation is reported separately as blocked. Executed verification needs actual required check evidence. |
| R-01 first Install versus missing Apply source | An authorized original specification/package and expected absent canonical destination permit new Install planning with future-source checks pending. The same absence under Apply/Invoke/Audit remains blocked. No mirror is consulted. |
| R-02 persisted plan truncation | Preserve key/dependency but remove or weaken an acceptance requirement, safety condition, or report destination in the stored verifier. Full-payload comparison rejects both newly created and existing records; metadata parity cannot pass. |
| R-03 cancelled or failed verifier | A matching key/dependency with cancelled/failed verifier state is an unresolved obligation, not sufficient already-exists success. Record an authorized retry/reopen/replan or blocked result; no silent replacement or activation. |
| R-03 stale or blocked verifier | A completed verifier with changed tested inputs or missing applicable evidence is stale, not an accepted pass. A blocked verifier remains blocked until readiness and its verified resume route resolve. Valid pending/running tasks may be reused without claiming a pass or launching replacements. |
| R-04 post-barrier primary change | Revise the primary after initial finalization readback and before/during attachment. Pre/post-link checks reject the old payload. Retain any created record with explicit stale/blocked handling and authorized repair, not silent deletion. |
| R-04 change before execution | After successful linkage, revise the primary plan or obligation baseline before verifier execution. Rebinding/readiness checks block substantive verification under the old plan. Report absent atomic scheduling controls honestly. |
| R-05 reference/specification drift | Change only a required transitive acceptance reference or pre-install specification attachment. Immutable manifests detect the drift even if root SKILL.md and primary-plan digests are unchanged. Reconcile obligations/evidence without silently replacing the duplicate key. |
| R-05 delivered-source evidence | Discover and manifest the installed reference closure after initial planned-source absence. Compare it to the pinned specification; initial availability does not change task identity. Material unplanned obligations require renewal. Changed implementation/configuration snapshots invalidate affected accepted results. |
| R-06 uncertain primary commit | Commit the primary but lose its create response. Trusted request/binding lookup recovers the authoritative record and uses the existing-primary barrier. No guessed ID or second primary write. Unknown/multiple records remain blocked. |
| R-06 uncertain verifier commit | Commit the verifier but lose its response. Authoritative lookup plus full reuse checks recover the real ID once; no blind retry. Definite non-commit differs from unknown outcome. |
| R-07 canonical key equivalence | Verified aliases for the same Project and equivalent unordered scope produce the same versioned key. Distinct semantic scopes, ordered meanings, or primary namespaces remain distinct. Unknown equivalence is reconciled, not guessed. |
| R-08 release without delivery | Release the host dependency using platform status while withholding delivered outputs. The execution readiness gate remains blocked, retains the obligation, and identifies the verified resume/recheck route; no successful verification or claimed platform scheduling gate. |
| Report-only mode reconciliation | "Fully apply" a report-only target without separately authorized implementation/task scope. Preserve Invoke/Audit mode and its report; create no automatic installation-verification tasks. Mixed authorized Install outcomes are reconciled separately. |
| Required companion missing | Discover an applicable required companion with no canonical source. Block its obligation instead of using a mirror, guessed alias, or optional exemption. An irrelevant/optional companion does not block. |
| Complete package installation | Install a skill whose SKILL.md requires bundled resources. Include the authorized resources at canonical relative paths; verify them independently. File-only confirmation repairs remain limited to SKILL.md. |
| Multi-target bundle | Reconcile every target/scope's actual primary, payload, key, lifecycle, dependency, and readiness. A single-target verifier cannot count for omitted bundle members; shared plans need explicit per-target coverage/bindings. |
| Completed primary reporting | Plan follow-up for a durably delivered primary with delivery evidence. Report verification pending and delivery already achieved, not falsely "skill not yet installed." |
| Verified-snapshot final acceptance | Change relevant inputs between a verification run and report acceptance. Invalidate affected evidence or report the exact earlier tested snapshot. Without verified isolation/final coordination, do not claim a concurrently changing current snapshot passed. |
| Verifier amendment after linkage | After successful full-payload readback, edit only the verifier's coverage, safety rules, or report path. Execution-time and report-acceptance full-payload comparison reject the substituted instructions despite unchanged primary/key/dependency. |
| Identity resolution discovery | Permit minimal authorized read-only evidence to identify the intended Project. Substantive target inspection/writes wait for confirmed identity; a standalone file-based plan does not require a task namespace. |
| Missing-source verification planning | An unavailable canonical target produces a staged blocked discovery plan/report without invented obligations. Planning delivery and future verification status are separate; a requested already extracted full matrix remains Partial/Blocked. |

For each host test, retain the exact task and plan references, finalization
evidence, selected Project/target/scope, verifier ID/dependency/key readback,
observed outcomes, and unavailable capabilities. No user-data or production
side effects are authorized by this matrix. Do not use invented task IDs as
evidence of real host integration.
