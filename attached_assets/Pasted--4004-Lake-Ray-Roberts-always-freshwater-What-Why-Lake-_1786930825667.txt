#4004 - Lake Ray Roberts always freshwater
What & Why
Lake Ray Roberts is correctly registered as freshwater in the preset catalog (FRESHWATER_PRESET_DATASETS in terrain.ts) and the seeded catalog entry preset-lake-ray-roberts, but two runtime paths can still classify a Ray Roberts save as saltwater:

DB backfill script — lib/db/src/scripts/backfill-water-type-and-datasource.ts blanket-writes waterType: "saltwater" to every legacy row lacking a water type, including catalog saves linked to Lake Ray Roberts that were saved before the freshwater feature and never re-opened. (This absorbs the scope of draft Task #3997.)
Legacy read-path fallback — resolveCatalogWaterType in artifacts/api-server/src/routes/user-datasets.ts resolves waterType only via the catalog DB row. When the preset-lake-ray-roberts DB row is momentarily absent (seeder reconcile purges/re-creates preset rows on boot) or the lookup errors, the route falls back to saltwater — even though the in-code preset registry (ALL_PRESET_DATASETS) authoritatively says freshwater. Catalog ids map to preset ids by stripping the preset- prefix (see catalogSeeder.ts).
A full repo audit found no other production code, catalog data, or generated bundle that pairs Lake Ray Roberts with saltwater — all remaining "saltwater" mentions near Ray Roberts are fixtures for other datasets (e.g. no-strategy-preset, preset-ocean, generic test grids) or comments, and need no change.

Done looks like
A legacy Lake Ray Roberts save always returns waterType: "freshwater" from the terrain and overview routes, even when the linked catalog DB row is missing or the lookup fails.
Running the backfill script assigns freshwater to legacy rows whose linked catalog save resolves to a freshwater entry (Ray Roberts included); only genuinely unlinked legacy uploads default to saltwater.
The legacy-compat test that previously locked in the saltwater fallback for a Ray Roberts-linked save now asserts freshwater; a generic unknown catalog id still falls back to saltwater.
Out of scope
Removing the read-path shim entirely (draft #3997 suggested this after a production backfill run; keep the shim as defense in depth).
Changing the saltwater default for legacy uploads with no linked catalog save — that default is correct.
The freshwater tidal-model work (Task #3770) and freshwater data-pipeline consolidation (Task #2767).
Any UI changes — the frontend already renders whatever waterType the API returns.
Steps
Preset-registry fallback in the read path — In resolveCatalogWaterType (user-datasets.ts), when the linked save's catalogId has no matching catalog DB entry (or the lookup throws), strip the preset- prefix and consult the in-code preset registry (ALL_PRESET_DATASETS from terrain.ts) before returning null. Ray Roberts then always resolves freshwater; unknown ids keep the saltwater default.
Fix the backfill script — Update backfill-water-type-and-datasource.ts to join userCatalogSavesTable and resolve waterType from the linked catalog entry (with the same preset-registry fallback) instead of blanket-defaulting every row to saltwater; keep saltwater only for rows with no resolvable link.
Update and extend tests — In user-datasets-legacy-compat.test.ts, add cases: legacy blob linked to preset-lake-ray-roberts with the catalog DB entry absent must return freshwater (terrain and overview); keep/adjust the generic gone-entry → saltwater case. Add a unit test for the backfill script's resolution logic (mock the db pool with the shared createDbPoolMock() helper; requireAuth test apps need the x-e2e-user-id bypass header).
